# Headmaster Constitution: Resuscitation Health App

## Mission
Headmaster exists to turn the current Warden-heavy repository into a durable four-authority operating system without erasing the project's clinician-facing, state-machine-driven character.

## Non-Negotiable Project Constraints
1. Preserve the product's `LIGHT_ONLY` identity unless a future ticket explicitly changes scope.
2. Preserve `MOBILE_PORTRAIT_390x844` as the primary design and evidence profile.
3. Treat the live product as a dynamic decision state machine, not a static page set.
4. Do not weaken `incoming / current / previous` zone clarity or clinician-safe forward/back navigation.
5. Do not replace project-specific evidence practices with generic Toolkit doctrine when they conflict.

## Authority Law
1. Warden remains the authority on current-state implementation and live evidence.
2. Headmaster defines future-state direction, source maps, syllabus, and handoff boundaries.
3. Switchboard routes delegates but does not replace Warden or Headmaster judgment.
4. Exit is the continuity compiler and must not be treated as strategy authority.

## Naming Law
1. Headmaster tickets use `HREQ-*` in this project.
2. Existing Warden `REQ-*` tickets remain canonical.
3. Headmaster handoffs should reference the Warden numbering scheme that already exists in this repo instead of renaming history.

## Closure Law
A Headmaster lane closes only when:
1. the ticket state and cycle log agree
2. the relevant source map or architectural document is updated on disk
3. the next bounded lane is clearer than before
4. any delegate work is reviewed through Steward or explicitly assigned otherwise
